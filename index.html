Why we build this

Attacks have moved past the smart contract.

$1.5B
Bybit, February 2025. The largest crypto theft on record. It did not start with a bug in the audited contract. It started with a developer's laptop.

A report certifies a commit, not a system

A conventional audit certifies code as it existed on one day. Upgrade a proxy or redeploy a service, and that report describes code which no longer runs. Almost no one tells the customer this.

Most reports do not say what they skipped

A list of findings looks like coverage. It is not. Without an explicit statement of scope and method, you cannot tell "this system is sound" from "we did not look there."

Where our line is

The pattern is consistent. Attackers increasingly target infrastructure, deployment pipelines and operator environments, methods that bypass traditional code audits. We are precise about which part of that is ours.

Endpoint and signing-environment compromise is not what AttackTrail stops. That is what ANAM145 SignTrail is built for. AttackTrail covers what is in the code and the configuration — a missing permission check, a drainable withdrawal path, and above all an upgrade that quietly breaks the rules the first review relied on.

We do not claim AttackTrail would have prevented any specific incident. The figure above is drawn from published reporting on the February 2025 Bybit incident.

How it works

Machine breadth. Human judgment.

Automation attempts every path. Two named people decide what is real.

STEP 01

Automated scan

AI and static analysis across the whole codebase, so the long tail of known vulnerability classes is attempted rather than sampled.

STEP 02

Expert triage

A specialist removes false positives and rates real business impact. Nothing reaches the report unreviewed.

STEP 03

Approver sign-off

A second named expert re-checks every finding before the report is released.

The reviewer is never the approver. If you review your own judgment, nothing catches the error "I saw it, and I judged it harmless." This separation holds on every engagement, and both names appear on the report.

Banks launching digital-asset services

You integrate a custodian, expose new APIs, and add signing and settlement paths. We review those boundaries, the permission model, and the code that moves value — and we state which paths we examined and which we did not, so your risk function has something auditable rather than a pass mark.

Wallets, exchanges and custody

Stablecoin rails and payment integrations depend on authentication, authorization and dependency hygiene as much as on contract logic. Objections, answered

The questions buyers actually ask

Is this a penetration test? +
No, and we do not describe it as one. This is a review-based assessment: we read code and configuration. For smart contracts we go further and reproduce each confirmed finding locally, so you get working proof. Penetration testing against running systems is a different discipline and opens in Stage 2. If a live-system test is what you need, we will say so rather than sell you a review.
Can I trust findings produced with AI? +
The AI never has the last word. It surfaces candidates with mandatory code citation; a specialist triages every one, and a second named expert approves the report. For smart contracts, a finding that cannot be reproduced does not ship. You are buying human judgment with machine reach — not a black box.
What about false positives? +
Two gates protect you. Human triage removes noise before anything is written up, and for contract findings a mandatory proof-of-concept means anything unreproducible is dropped. Web and API findings are labelled as risk indicators rather than proven exploits, so you know which ones still need active testing to confirm.
What if you miss something critical? +
No review — human or automated — can promise zero misses, and we will not pretend otherwise. What we give you is a written scope with explicit exclusions, a coverage statement showing exactly what was examined and by which method, and a fix-verification pass. You know precisely what we checked and what we did not.
Do you need access to our production systems? +
No. Source code and documentation are sufficient, and no traffic is sent to a running system. That is a deliberate property of a review-based service: you can evaluate us without operational risk. Any active testing would require separate written authorization, and that belongs to Stage 2.
How do you scope and price an engagement? +
From measured code size, using logic lines only — no comments, blanks, imports, tests or library source — normalized so that reformatting your code never changes the number. We then weight the parts that genuinely take longer: interface-only files count less, upgrade paths and novel math count more, inline assembly most of all. You receive the per-file measurement table, the tool version, and the command to reproduce the count yourself.
What happens after we deploy? +
This is the gap almost nobody covers. An audit certifies a commit; the moment you upgrade a proxy, the report describes code that no longer runs. Stage 3 monitors the deployed system for change — upgrade events, bytecode changes, permission transfers — and re-assesses whatever changed against the original review, integrated with ANAM145 SignTrail.
Which tools and models do you use? +
Every engagement includes a methodology appendix naming the analysis techniques, tool versions and model roles applied to your codebase. Institutional buyers do not buy black boxes, so we do not ship one.
